0. System overview

The teacher phi3.5 (Phi-3.5-mini-instruct, 3.8B, Ollama, temperature 0, seed 42) labels 3,000 SLURP commands with a four-key JSON frame. The student EleutherAI/pythia-70m is fine-tuned on the teacher's replies (sequence-level KD) and served by a FastAPI service. Everything runs on one single-node k3d cluster (k3s v1.30.6) on the laptop used for this project (8 vCPU, 15 GiB RAM, Docker), in three namespaces: data (SeaweedFS S3 with buckets datasets and models), pipeline (teacher workers as an Indexed Job) and app (Deployment, Service, Traefik Ingress, HPA). The laptop could not run the 3.8B teacher over 3,000 commands in the available time, so Ollama ran on a free Google Colab T4 and was reached by the in-cluster workers through a free Cloudflare quick tunnel (OLLAMA_URL); model, prompt and settings are unchanged. Training and evaluation ran on the laptop CPU (4 cores). CI runs on free GitHub Actions. Because another program occupies host port 8080 on that laptop, the local cluster mapped the Ingress to host port 28080; cluster/k3d.yaml in the repository uses 8080, so the standard Locust command works unchanged on a fresh machine.

Task 1: Object storage and parallel teacher labelling

Architecture. make up creates the cluster from cluster/k3d.yaml, deploys SeaweedFS (single weed server -s3 pod, PVC, NodePort) in data, creates both buckets and uploads commands_pool.jsonl to datasets (results/storage_init.log). S3 credentials are generated per cluster into the git-ignored .secrets/ and loaded as Kubernetes Secrets. The prompt is prompts/teacher_prompt.txt (eight intents with meanings, the three slot rules, six examples taken from the handout, "JSON only"); it is mounted into the workers from a ConfigMap, so the workers always use the committed prompt. Ollama is called with format: "json".

Sharding. worker/worker.py reads SHARD_INDEX and SHARD_COUNT and keeps the commands whose 0-based line number n satisfies n mod SHARD_COUNT = SHARD_INDEX. The workers run as one Indexed Job in pipeline with completions = parallelism = 3; each pod's SHARD_INDEX is its completion index (downward API), so the three shards are disjoint and together cover every line. Modulo (rather than contiguous blocks) balances the load even if the file is sorted, and needs no knowledge of the file length. Each worker writes its own object datasets/teacher/shard-<i>.jsonl and checkpoints every 25 records, so a restarted pod resumes instead of starting over (useful because the teacher sits behind a tunnel). scripts/check_shards.py confirmed Measured 3 × 1,000 records, 3,000 unique ids, 0 missing, 0 repeated. Wall time Measured: about 26 min for 3,000 commands (3 workers, ~1.5 s per request each).

Cleaning. worker/clean.py reads all shards, sorts by id and applies rules (a)-(d) in order (a record is counted under the first rule it breaks), then removes duplicate commands among the survivors (text lower-cased and whitespace-normalised; smallest id kept). Slot rule (d) accepts null or a non-empty string that occurs in the command (case/whitespace-insensitive). Each kept line stores the teacher's reply unchanged (teacher_raw) plus the same frame re-serialised on one line (target), which is the training target. Re-running clean.py on the committed shard files reproduces the checksum in train.sha256: d80d7e7bc4073d80… Measured.

Task 2: Training the student (sequence-level distillation)

Implementation. training/train.py (PyTorch + Transformers, CPU) reads only training/config.yaml (seed 42, learning rate 3e-4, batch 16, 10 epochs, max length 128, library versions) and trains on the first 1,500 records of train.jsonl (its SHA-256 is verified first). Each example is Command: <text>\nJSON: <teacher JSON><eos>; the loss is computed only on the JSON part (prompt tokens masked). The seed is fixed in code (Python, NumPy, PyTorch, data-loader generator). make train SUBSET=50 trains on 50 records. v2 = the same settings with one more epoch (training/config_v2.yaml). training/publish.py writes model.sha256 and uploads model, tokenizer, version.json and checksums to s3://models/v1/ and v2/; the same files are the assets of GitHub Releases model-v1 and model-v2. The downloaded Release model.safetensors matches models/v1/model.sha256 (3fdebaf0da34c011…; results/release_v1_checksum_verify.txt) Measured.

All numbers Measured. What changed. The untrained model continues the text with unrelated prose or a lone "{"; it never produces the format (0% everywhere). After distillation the student reproduces the frame format almost perfectly and copies slot phrases from the command. Its full-frame score (52%) is close to, here even slightly above, the teacher's (46%): it learned the teacher's behaviour, including its labelling conventions, and on 100 examples a few points are within noise. The student cannot be better than the teacher in general; the gap to the gold labels (intent 83%) is inherited from the teacher (83%).

Sequence-level vs. logit-based distillation. (a) Sequence-level KD (Kim & Rush, 2016) trains the student with ordinary cross-entropy on the teacher's generated output sequence, i.e. the teacher's single best answer is the hard target. (b) Logit-based (token-level) KD trains the student to match the teacher's full probability distribution over the vocabulary at every position (e.g. KL divergence between softened teacher and student logits), which also transfers how confident the teacher was in the alternatives. (c) It is not possible here because the teacher is used only through Ollama's generate API, which returns text, not per-token distributions; moreover phi3.5 and Pythia use different tokenizers/vocabularies, so their distributions are not position-by-position comparable without an alignment step. (d) A real limitation of this approach: the student learns only the teacher's top-1 answer, including the teacher's mistakes (e.g. the 139 normalised slots that were filtered out show the teacher's systematic errors; the ones that pass the filter are learned as truth), and nothing about uncertainty; a 70M model also falls into repetition loops on a few inputs (2/100 on validation in strict mode).

Task 3: The inference service in a container

Implementation. service/app.py (FastAPI, uvicorn, port 8000). Configuration comes only from MODEL_URI, MODEL_VERSION, S3_ENDPOINT, MAX_NEW_TOKENS (+ FAULT_INJECT); credentials (AWS_ACCESS_KEY_ID/SECRET) come from the Secret s3-credentials. At start-up a background thread downloads every object under MODEL_URI from SeaweedFS and loads the model; /healthz answers 200 at once, /readyz answers 503 until the model is loaded. POST /parse runs greedy decoding (prompt Command: ...\nJSON:), cuts the text at the first newline/closing brace and checks it against schema.json (exactly the four keys, intent in the eight, slots null or string). If that strict check fails, a deterministic salvage step takes the first allowed intent and the first value of each slot from the model's own text, keeping a slot only if it occurs in the command (else null); if no allowed intent exists, the service returns 500 {"error": "invalid_model_output"}. Valid responses carry X-Model-Version and X-Served-By (Pod name from the downward API). With FAULT_INJECT=1 the output is replaced by not json before checking and the service returns exactly that 500 body Measured. The image (python:3.11-slim, CPU-only PyTorch wheel, every dependency pinned in service/requirements.txt, pip install --no-deps) contains no weights (0 weight files found) and is 1.69 GB Measured; it builds from a fresh clone with make images or docker build -f service/Dockerfile ..

Running under limits (docker run --cpus=1 --memory=1g --memory-swap=1g, 50 sequential requests, results/task3_container.log) Measured: status codes {200: 50}; median latency 390 ms, max 892 ms; peak memory 816.5 MiB (cgroup memory.peak, includes page cache of the 282 MB weight download); OOMKilled = false. Before the salvage step was added, the same test gave 49 × 200 and 1 × 500 (results/before_salvage/task3_container.log).

Limitations / improvements. Weights are stored in float32 (282 MB); float16/int8 would halve start-up download and memory. Generation is serialised by a lock (one request at a time per pod, by design for a 1-CPU limit). Salvage hides a model weakness; constrained (grammar-guided) decoding would remove it at the source.

Limitations. This is a single-node cluster on one laptop: it demonstrates Pod-level recovery, not fault tolerance across machines (losing the laptop loses everything, including SeaweedFS, which is a single replica on a local-path volume). HPA max 2 × 1 CPU limit and the host's other load bound throughput; metrics-server reports with a ~15-60 s delay, so scale-up lags the load. Assumption Behaviour on a multi-node cloud cluster would differ (image pulls, network latency).

NACL of the public subnet (network/nacl.json). Inbound: 50 deny all from 198.51.100.0/24; 100/110 allow TCP 80/443 from 0.0.0.0/0; 120 allow TCP 22 from management 10.20.5.128/27; 130 allow TCP 1024-65535 from app 10.20.0.0/22 (replies from the app's port 8000 to the load balancer's ephemeral ports); everything else falls to the default deny. Outbound: 100 allow TCP 8000 to 10.20.0.0/22; 110 allow TCP 1024-65535 to 0.0.0.0/0 (replies to clients' ephemeral ports). nacl_sim.py --check on packets_sample.jsonl: 6 / 6 = 100.0% Measured.

Why replies need their own rules. A NACL is stateless: it does not remember that it allowed a request, so the reply packet is checked again on its own, against the rules of its direction. A client's request to port 443 is allowed inbound, but the answer travels outbound to the client's ephemeral port (1024-65535), and the app's answer to the load balancer arrives inbound on the balancer's ephemeral port; without rules 110 (outbound) and 130 (inbound) those replies would hit the default deny. Why order matters. Rules are evaluated from the lowest number and the first match wins. A packet from 198.51.100.9 to port 443 matches both "deny 198.51.100.0/24" and "allow 443 from anywhere"; the deny only works because its number (50) is lower than the allow (110). Numbered after the allow, it would never be reached.

Task 6: Reproducibility, testing and CI/CD

Reproducibility. From a fresh clone: git clone https://github.com/Arunendra21/kd-command-parser.git, cd kd-command-parser, make up (3 commands). make up creates the cluster, secrets, SeaweedFS, buckets and dataset, builds and imports both images, downloads model-v1/model-v2 from GitHub Releases (verifying model.sha256) into s3://models/, and deploys the app; make down deletes the cluster. A Codespaces devcontainer.json provides Docker, k3d, kubectl and gh. CI (.github/workflows/ci.yml), stages in order: lint (ruff) → unit tests (16 pytest tests: schema validation, salvage, cleaning rules (a)-(e) and count identity, sharding coverage, API headers/FAULT_INJECT/readiness, NACL) → evaluation (downloads the model from the GitHub Release, verifies its checksum, runs predict.py + score.py on validation) → quality gate (score.py --min-validity 95), plus a gitleaks secret scan (reports no leaks) Measured.

The gate doing its job Measured: run with the deliberately bad model (untrained Pythia-70M) fails at the quality gate with QUALITY GATE FAILED: json_validity 0.0 < 95.0: https://github.com/Arunendra21/kd-command-parser/actions/runs/42193836249. The same workflow with model-v1 passes all stages: https://github.com/Arunendra21/kd-command-parser/actions/runs/42193828050. AI use is documented in AI_USE.md.

Limitations / improvements. CI does not start a cluster; an end-to-end job (k3d inside the runner, Locust smoke test) would catch manifest regressions. Images are built locally and imported, not pushed to a registry.
